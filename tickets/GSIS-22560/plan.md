# Part 1 — Understanding

## Problem

On **Exam Controller → Masters → Component Type**, the "Component ID" (`componentCode`, `CMP-0001`, `CMP-0002`, …) is generated by the backend on create. When a row is saved (row Save or Save All) the generated number can jump ahead of the existing ones, so the IDs are no longer in sequence with the rows on the screen.

## Expected / Observed

- **Expected** (ticket): the next component created gets the number immediately after the highest one already in use; IDs follow the order in which rows are created.
- **Observed** (recording): the list's highest ID is `CMP-0063`; after adding and saving one row, the new row gets **`CMP-0065`** — `CMP-0064` is not in the list. The count of components in the context assignment (64) is already ahead of the highest visible code (63), and the generator uses that count.

## Root cause (bug)

**The component ID is numbered from a row *count* instead of from the highest existing code:** `ComponentTypeServiceImpl.preCreateEntity` builds `String.format("CMP-%04d", countComponentByStructureAssignment(contextAssignmentId) + 1)` (`ComponentTypeServiceImpl.java:90-96`) from a non-atomic native `COUNT(*)` read once per request before the row is inserted (`ComponentTypeRepository.java:8-14`), so once two concurrent saves have read the same count and minted the same code, the count permanently exceeds the highest code and **every later create skips a number** — the `CMP-0063 → CMP-0065` jump in the recording.

Evidence:

1. Generation site: `ComponentTypeServiceImpl.java:90-96` — `size = count(...) + 1; code = String.format("CMP-%04d", size); entity.setComponentCode(code)`. (Re-read by the orchestrator at `origin/base-development`: matches.)
2. The count is a native query with **no `deleted` filter on either table and no lock** (`ComponentTypeRepository.java:8-14`). Its only caller is line 91 (orchestrator-verified).
3. Generation runs inside `BaseService.createAndGetEntity` (commons `gears-commons-lib-0.0.33`; `validateRequest → validateAndMapToEntityForSave → preCreateEntity → repository.save → postCreateEntity`) with no surrounding transaction or unique constraint, so overlapping requests read the same count and persist the same code.
4. `component_code` is a plain `VARCHAR` with **no unique constraint** (`src/main/resources/db/changelog/V2/1-table_modifications/001353-create-sis-exam-component-type-master-table.xml`).
5. The displayed "Component ID" is `componentCode`, not the DB `id` (`src/main/resources/i18n/examination/en.json:915`).
6. The recording's arithmetic is consistent with the root cause: new row `CMP-0065` while the highest visible is `CMP-0063` ⇒ count was 64 for that assignment.
7. Row Save is already guarded on base: commit `aa7425dbb7` "GSIS-19877: prevent multiple inline save causing id skip in component type" (2026-04-20 13:19 +0530, in `origin/base-development`, orchestrator-verified) added the `isLoading()` guard, after this recording was taken; it cannot repair a count/max divergence already in the data. `saveAll()` never got the guard (orchestrator-verified).

Alternatives ruled out:

- **Client-side ID generation / stale UI** — the new inline row has `componentCode: ''` (`onAddButtonClicked`); the row is replaced by the server payload.
- **Database sequence/identity gap** — the displayed ID is not the autoincrement `id`; no sequence is attached to `component_code`.
- **Soft delete alone** — see the orchestrator note below: the plan claims delete on its own produces no skip; the note qualifies that.
- **Sorting/pagination illusion** — `CMP-0064` is absent from both pre-save and post-save frames of a code-descending list.
- **Bulk/import path minting codes differently** — the count query has one caller; no bulk-save endpoint exists for component type; other consumers are read-only.

# Part 2 — Plan

## Decisions

- **Following:** D-1 (routing).
- **New:**
  - **D-2 Root cause** — count-based, non-atomic code generation at `ComponentTypeServiceImpl.java:90-96` / `ComponentTypeRepository.java:8-14`.
  - **D-3 Fix approach** — derive the next code from the **highest existing code in the same context assignment (including soft-deleted rows) + 1**, following the in-repo precedent `RoleServiceImpl.generateRoleID` / `MiscUtils.extractNumericPart`, and add the existing `isLoading()` re-entry guard to `saveAll()`. Rejected: (a) unique index on `component_code` + retry — needs Liquibase and fails on environments that already hold duplicates; (b) DB sequence / advisory lock / new `@Transactional` boundary around a shared base-class flow — too broad for a P4 bug; (c) frontend-only guard — cannot repair a count/max divergence nor cover a second browser or user; (d) backfilling existing codes — out of scope (Q1).
  - **D-4 Test strategy** — a backend regression test that seeds an assignment whose row count exceeds the highest code and asserts the next code is `max + 1` (fails on current code, which yields `count + 1`), plus a frontend spec for the Save All re-entry guard; recorded commands and real results.
  - **D-5 Known limitation (accepted)** — after this fix two genuinely simultaneous creates (two users/tabs, same assignment) can still mint the same code; a durable guarantee (unique constraint + retry, or a shared sequence) is a follow-up with Q3.
- **Superseding:** none.
